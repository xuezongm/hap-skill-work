# Skill 维护规范

## 目标

让每条内容只有一个权威归属，使目标 Skill 对人好读、对 Agent 好执行，并能按任务渐进加载。

## 强制读取

开始分析前完整读取 `references/content-governance.md`。该文件定义文件职责、写入程度、禁止内容、单一事实源和归档决策规则。

## 工作模式

根据用户意图选择模式：

- **审查**：只读取和报告，不修改文件；
- **方案**：输出目标结构、迁移清单和验收标准，不修改文件；
- **实施**：完成约定范围内的修改并验证；
- **新增内容**：先判断权威归属，再写入目标文件及必要引用。

用户只要求检查、解释或出方案时，不得自行进入实施模式。

## 维护流程

### 1. 确认目标与本地约束

1. 确认目标 Skill 根目录，不得把维护规范误写进被维护 Skill；
2. 读取适用的 `AGENTS.md`、目标 `SKILL.md` 和仓库说明；
3. 保留工作区现有修改，不自动提交或推送；
4. 若目标目录不是 Skill 或存在多个候选目标，先通过只读检查消除歧义。

### 2. 建立文件地图

盘点以下内容：

- 入口与场景路由；
- 工作流、步骤和阶段门禁；
- Guide、Spec、安全规则、执行边界和 Schema；
- scripts、references、assets、agents 元数据；
- 文件之间的引用和运行时加载规则；
- 路由决定、机器契约、生产者、校验者和消费方；
- 必须生成的运行产物及其完成门禁；
- 过长文件、未引用文件、失效引用、重复规则和职责混杂。

先运行只读检查：

```bash
python3 {SKILL_DIR}/scripts/audit_skill.py {TARGET_SKILL_DIR}
```

脚本结果只作为线索。语义重复、职责冲突和内容粒度必须人工判断。

### 3. 建立权威归属表

对准备新增、修改或迁移的每类内容，记录：

| 内容 | 唯一权威文件 | 使用方 | 加载时机 | 处理方式 |
|---|---|---|---|---|
| 规则或知识点 | 实际文件路径 | 哪些文件引用它 | 何种任务/阶段读取 | 保留、迁移、合并或删除 |

同一规则只能有一个完整定义。其他文件只保留完成路由所需的短摘要和明确引用。

若一次变更会跨越多个文件，再建立契约影响表：

| 契约 | 权威定义 | 生产者 | 校验者 | 消费方/产物 | 回归用例 |
|---|---|---|---|---|---|
| 路由、结果字段或检查项 | 定义语义的文件 | 谁产生该值 | 谁拒绝非法值 | 谁读取或展示 | 哪些请求或样例必须通过 |

“单一事实源”不表示一个完整功能只能写在一个文件中。不同文件可以分别负责定义、执行、校验和展示，但同一语义不得在多个文件重复定义。

### 4. 决定内容归档位置

按内容回答的核心问题分类：

- “何时触发、进入哪里” → `SKILL.md`；
- “先做什么、何时停止” → workflow；
- “一个原子任务怎样完成” → step/SOP；
- “某类对象应检查和怎样处理” → Guide；
- “参数、字段、枚举和合法结构是什么” → Spec；
- “任何路径都不能绕过什么” → safety rules；
- “复杂操作何时自动、协同、人工或阻断” → execution boundaries；
- “审查什么、适用于什么对象、需要什么证据” → Audit Checks；
- “通过什么接口、读取多深、何时补抓或停止” → evidence collection guide；
- “产物必须满足什么机器结构” → Schema/contract；
- “怎样做确定性检查或转换” → script；
- “本次实际取得了什么证据和结论” → runtime artifacts；
- “供产物复制使用的文件” → asset；
- “用户如何理解和使用该 Skill” → README/界面元数据。

无法唯一归类时，先拆分内容，不要把多种职责塞进同一章节。

### 5. 实施最小修改

1. 先修改权威文件，再修改引用方；
2. 契约变化时同步更新必要的生产者、校验者、消费方和回归用例；
3. 新增文件时同步更新入口、加载映射和校验清单；
4. 迁移内容时删除旧文件中的完整副本，只留下必要引用；
5. 案例只解释容易误用、存在分支或高风险的规则；
6. 不为追求形式统一而给每类对象机械增加同样的小节；
7. 不改动用户未授权的业务规则和无关文件。

### 6. 验证

实施后至少完成：

1. 再次运行 `audit_skill.py`；
2. 运行目标 Skill 自带的校验、测试或上下文解析器；
3. 使用官方 `quick_validate.py` 校验 Skill 结构（若当前环境可用）；
4. 检查新增引用可达、旧引用已清理、权威定义无重复；
5. 按变更类型执行行为回归：路由变更覆盖正例、反例和易混淆表达；契约变更验证生产、拒绝和消费；强制产物验证缺失时不能宣告完成；
6. 用一个真实触发请求验证加载文件足够且没有明显过载。

## 交付要求

结果必须说明：

- 哪些文件被新增、修改、迁移或删除；
- 每项内容的最终权威归属；
- 删除了哪些重复或不必要内容；
- 哪些检查通过，哪些问题仍需人工判断；
- 是否执行了提交或推送。

不要只报告“已优化”，也不要把脚本警告直接当作事实结论。
