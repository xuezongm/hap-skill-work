# Skill 内容治理规范

本规范用于判断 Skill 中每类文件的职责、相互关系、写入内容、内容深度和禁止内容。目录名称可以不同，但职责必须能够一一对应。

## 1. 核心原则

### 1.1 单一事实源

每条规则、参数定义、枚举、流程顺序或安全底线只能有一个权威文件。引用方允许保留一句完成路由所必需的摘要，但必须指向权威来源，不能复制完整定义。

判断标准：修改一条规则时，如果需要在多个文件中同步修改完整正文，说明职责尚未分清。

### 1.2 按需加载

入口只负责找到正确流程；流程只加载当前阶段需要的规则；对象规范只在命中该对象时读取。不要因为“可能有用”就把所有参考资料放进根 `SKILL.md` 或每个工作流。

### 1.3 内容就近归属

内容归属于能够回答其核心问题的文件，而不是归属于最常被打开的文件：

- 触发与路由回答“何时进入”；
- 工作流回答“按什么顺序”；
- Guide 回答“要考虑什么、怎样处理”；
- Spec 回答“合法结构是什么”；
- Safety 回答“什么绝不能做”；
- Boundary 回答“在什么条件下能由谁执行”；
- Schema 回答“机器产物长什么样”。

### 1.4 最小充分

内容应详细到 Agent 能做出一致决策并验证结果，但不重复其他权威来源。满足以下条件即可停止扩写：

1. 能判断何时适用；
2. 能知道必要输入和输出；
3. 能识别停止条件；
4. 能找到参数权威来源；
5. 能验证是否完成。

### 1.5 契约链一致

一个功能可以由多个职责文件共同实现，例如 Workflow 定义何时生成结果，Contract 定义结果结构，Script 校验结果，报告消费结果。此时应把它们视为一条契约链，而不是强行合并成一个文件。

契约链仍遵守单一事实源：每个语义维度只在一个位置定义。引用方负责执行或消费，不得重新解释字段含义、检查适用范围或评分规则。修改契约时必须同时检查生产者、校验者、消费方和行为用例。

## 2. 文件职责矩阵

| 文件角色 | 主要回答 | 应写入 | 写入程度 | 不应写入 |
|---|---|---|---|---|
| 根 `SKILL.md` | 何时触发、路由到哪里 | description、前置条件、场景路由、最短主流程、必须读取的文件 | 保持短小；足够选择路径和启动任务 | 参数百科、大量案例、完整对象规则、重复工作流细节 |
| Workflow | 整个场景按什么顺序执行 | 阶段、输入输出、门禁、停止点、确认点、引用加载时机 | 覆盖端到端流程，但每阶段只写流程职责 | 对象参数表、底层 payload、大量业务案例、另一个工作流的全文 |
| Step / SOP | 一个原子任务如何完成 | 前置输入、调用顺序、产物、局部失败处理、回读断言 | 执行者无需猜测即可完成该步骤 | 全局路由、跨场景政策、与本步骤无关的对象规范 |
| 对象操作 Guide | 某类对象变化会影响什么、应如何修改和验证 | 关联影响、对象特有的读写规则、验证点、高价值案例 | 覆盖业务决策和操作骨架；参数细节引用 Spec | 全局执行流程、完整参数枚举、通用安全规则、普通案例堆积 |
| 设计 Guide | 什么方案更合理 | 设计原则、选择标准、权衡、反例 | 支持判断即可，允许解释原因 | MCP 参数、执行门禁、固定工具清单 |
| Spec | 合法参数和对象结构是什么 | 字段、类型、枚举、约束、兼容关系、最小正确示例 | 对接口合法性完整，示例聚焦结构 | 业务流程、风险确认、角色分工、与参数无关的长篇设计说明 |
| Safety Rules | 哪些底线不可绕过 | 规则 ID、触发条件、强制要求、阻断条件、最低验证 | 短、硬、可判断；每条规则独立 | 教程、普通建议、平台参数百科、重复案例 |
| Execution Boundaries | 复杂操作何时可以自动执行 | 场景定义、风险证据、自动/协同/人工/阻断条件 | 详细到能确定执行方式和停止点 | 普通对象修改方法、静态工具库存、全部安全规则副本 |
| Schema / Contract | 机器产物必须满足什么结构 | 字段、类型、必填项、枚举、条件约束 | 对机器校验完整；描述简洁准确 | 叙事教程、执行案例、无法校验的宽泛建议 |
| Audit Checks | 审查什么以及适用于什么对象 | 检查项、主要对象或适用范围、证据要求、严重度、判定和建议 | 能稳定筛选检查项并重复得到相近结论 | 接口调用顺序、自动修复流程、写操作授权、目标对象完整 Spec |
| Evidence Collection Guide | 怎样取得足够证据 | 接口用途、读取层级、补抓条件、失败与通过的停止条件、落盘规则 | 足够支持检查项取证，优先最小必要读取 | 检查项正文、严重度、评分、报告章节或路由定义 |
| Script | 怎样确定性地检查或转换 | 可重复算法、参数、退出码、结构化输出 | 错误信息清楚，可独立验证 | 依赖语言模型判断的业务政策、秘密、写死的临时路径或真实 ID |
| Runtime Artifacts | 本次运行实际取得了什么 | 原始证据、结构化结果、报告和必要状态 | 真实、可追溯，与当前运行隔离 | 规范性规则的唯一副本、虚构证据、用于影响后续运行的隐藏指令 |
| Reference resource | Agent 完成某类任务需要查什么 | 稳定知识、资料、术语、规则来源 | 按主题拆分并在入口中说明读取条件 | 无引用的资料堆、与任务无关的背景知识 |
| Asset | 产物需要复用什么 | 模板、图片、字体、样板文件 | 可直接复制或加工使用 | 需要作为指令阅读的规则正文 |
| README | 用户如何理解和使用 | 能力概览、目录说明、安装和示例入口 | 面向人，保持概览级 | Agent 强制指令的唯一副本、完整内部 SOP |
| `agents/*.yaml` | Skill 在产品界面如何展示 | 显示名、简述、默认提示等元数据 | 与 `SKILL.md` 能力一致 | 业务规则、秘密、只存在于界面而入口未知的能力 |

## 3. 常见文件之间的关系

推荐加载关系：

```text
用户请求
  → SKILL.md（识别场景）
      → workflow（建立执行顺序）
          → step / Guide（当前任务怎样处理）
              → Spec / Safety / Boundary（参数、底线和能力边界）
                  → script / asset（执行确定性工作或复用产物）
```

Schema 通常由 workflow 或 step 约束产物；Audit Checks 通常由 audit workflow 加载。README 和维护规范面向使用者或维护者，默认不进入业务运行上下文。

Audit 场景推荐关系：

```text
SKILL.md（识别全量、定向或快速模式）
  → audit workflow（锁定范围、组织阶段、要求结果与报告）
      → audit checks（筛选检查项及其适用对象）
          → collection guide（按检查项取得最小充分证据）
              → validator/calculator（校验契约并做确定性计算）
                  → results/report/evidence（本次运行产物）
```

Workflow 不应长期手工维护某类对象对应的完整检查 ID 清单；检查适用关系应由 Audit Checks 的“主要对象”或等价字段定义，Workflow 只描述筛选方法和执行顺序。

### 3.1 引用规则

- 上层文件引用下层权威来源，不复制其完整内容；
- 同层文件按职责引用，避免双向依赖；
- 引用必须说明“何时读”和“用于什么”，不能只列文件名；
- 新增参考文件后必须接入实际加载路径，否则属于孤立文档；
- 删除或重命名文件时同时修正所有引用、脚本映射和目录说明。

### 3.2 冲突判断

不同文件管理不同维度，不建立一个粗暴的全局优先级。发生冲突时按问题类型确定权威来源：

| 冲突问题 | 权威来源 |
|---|---|
| 当前环境是否有某工具、工具接受哪些参数 | 当前运行时工具定义 |
| 产物结构是否合法 | Schema / Contract |
| 是否允许执行 | Safety Rules 与 Execution Boundaries |
| 执行先后顺序 | Workflow |
| 对象特有的修改和验证方式 | 对象 Guide |
| 字段、枚举和参数组合 | Spec |
| 设计是否合理 | 设计 Guide |
| 审查规则、主要对象、证据要求和严重度 | Audit Checks |
| 证据接口、读取深度、补抓与停止条件 | Evidence Collection Guide |
| 本次是否已经生成必要产物 | Workflow 的完成门禁与实际运行目录 |

若两个同职责文件给出不同结论，必须合并或明确一个权威来源，不能靠“优先读取某文件”长期掩盖冲突。

## 4. 内容粒度

### 4.1 规范性内容

使用明确的触发条件、动作和结果：

```text
当……时 → 必须/禁止…… → 通过……验证
```

避免“注意一下”“合理处理”“视情况优化”等无法执行或验证的表述。推荐项必须与强制项分开。

### 4.2 解释性内容

只在以下情况解释原因：

- 不解释就容易采取相反操作；
- 存在明显权衡；
- 平台行为反直觉；
- 需要帮助维护者判断未来变更是否仍适用。

能由规则直接推出的重复解释应删除。

### 4.3 案例

案例用于展示规则组合，不用于代替规则。只保留以下案例：

- 容易误用或具有分支；
- 涉及高风险、迁移或人工协同；
- 多个对象必须连带处理；
- 单看参数无法理解正确顺序。

普通增删改不需要每章都配案例。案例使用虚构 ID 和最小数据；完整 payload 只在它本身是学习重点时出现，否则引用 Spec。

### 4.4 重复摘要的允许范围

满足以下全部条件时，可以在引用方保留摘要：

1. 不保留就无法正确路由或识别阻断点；
2. 摘要不超过完成当前决策所需的信息；
3. 明确链接权威文件；
4. 不重新维护参数表、枚举或完整步骤。

## 5. 新增内容归档决策

按顺序判断：

1. 是否已有同义规则？有则修改权威来源，不新建副本；
2. 是否改变触发或路由？写入口；
3. 是否改变阶段顺序或门禁？写 Workflow；
4. 是否只影响一个原子步骤？写 Step；
5. 是否属于对象影响、处理或验证？写对象 Guide；
6. 是否属于参数合法性？写 Spec；
7. 是否是不可绕过的底线？写 Safety；
8. 是否用于决定自动、协同、人工或阻断？写 Boundary；
9. 是否能机器校验？写 Schema 或 Script；
10. 是否仅帮助理解复杂规则？作为权威规则旁的案例；
11. 若同时命中多项，拆成多个职责单一的片段，并建立引用。

## 6. 禁止写入的内容

任何 Skill 文件都不应包含：

- 密钥、令牌、真实凭据和不必要的个人数据；
- 无法确认来源的当前平台能力或静态工具清单；
- 可从运行时读取却长期写死的真实对象 ID；
- TODO、模板占位符、未解释的“后续补充”；
- 为显得完整而复制的规则、参数表或案例；
- 没有触发条件、执行动作或验证方法的绝对命令；
- 未经用户授权的提交、推送、发布或破坏性操作；
- 依赖不可用环境、临时绝对路径或维护者本机状态的指令。

## 7. 修改与迁移原则

### 7.1 修改现有规则

1. 找到唯一权威定义；
2. 列出所有引用方和加载映射；
3. 先改权威定义；
4. 只在引用方的路由语义变化时同步修改摘要；
5. 运行断链、结构和行为验证。

### 7.2 修改跨文件契约

先识别变更类型，再检查完整影响链：

| 变更类型 | 权威定义 | 必查联动 | 最低行为验证 |
|---|---|---|---|
| 触发词、范围或模式路由 | 根 `SKILL.md`，复杂判定下沉 Workflow | 路由锁、结果字段、报告口径 | 正例、反例和一个易混淆请求 |
| 结果字段或枚举 | Schema/Contract；无独立 Schema 时为 Workflow 中的结果契约 | 结果生产、校验脚本、报告消费 | 合法样例通过，缺失或非法样例被拒绝 |
| Audit 检查项 | Audit Checks | 检查项解析、适用范围筛选、评分或覆盖计算 | 新检查被正确选中，旧结果不会被误判 |
| 证据来源或读取深度 | Evidence Collection Guide | 证据落盘、结果引用、覆盖统计 | 证据充分时停止，证据不足时不得判 `pass` |
| 强制运行产物 | Workflow 完成门禁 | 产物命名、回读、最终回复 | 缺少产物时不得宣告完成 |
| 确定性算法 | Script | 输入契约、输出消费方、错误信息 | 固定输入得到固定输出，非法输入失败 |

联动不等于复制正文。只修改承担相应职责的部分，并删除为了同步方便而产生的第二份完整定义。

### 7.3 拆分过长文件

只有在内容具有不同加载时机或不同职责时拆分。单纯按行数平均切割会增加跳转成本。

适合拆分：

- 大部分任务只需要其中一个主题；
- 参数规范和业务流程混在一起；
- 安全底线被埋在大量案例中；
- 文件的不同章节由不同场景维护。

不适合拆分：

- 拆开后每次任务仍必须全部读取；
- 新文件只有几条内容且没有独立职责；
- 只是为了目录看起来整齐。

### 7.4 合并文件

满足以下任一条件时考虑合并：

- 文件总是同时加载且共同回答一个问题；
- 两个文件频繁重复或互相引用才能理解；
- 边界长期无法说清，修改时总要同步维护。

合并后仍需保留清晰章节，不把流程、参数和安全规则混成一篇长文。

## 8. 维护验收清单

### 职责

- 每个文件能用一句话说明唯一职责；
- 每条新增规则都有唯一权威文件；
- 没有为了格式统一而创建空洞章节。

### 引用和加载

- 所有引用路径存在；
- 新文件已接入实际加载路径；
- 没有不必要的全量加载和明显循环引用；
- 删除、移动和重命名后的旧引用已经清理。

### 内容

- Workflow 不含参数百科；Spec 不含端到端流程；Guide 不复制安全规则；
- 强制、推荐、人工和阻断能够区分；
- 案例使用虚构数据，并只覆盖高价值场景；
- 当前能力以运行时为准，没有过期工具清单。
- Audit 的检查适用关系没有在 Workflow 中重复维护完整 ID 清单；
- 运行产物只记录本次事实，没有成为规范性指令来源。

### 可执行性

- 触发条件、输入、动作、停止条件和验证方法明确；
- 机器产物有 Schema 或等价契约；
- 脚本退出码和错误信息可理解；
- 契约变化已经验证生产者、校验者和消费方；
- 路由变化至少验证正例、反例和易混淆表达；
- 强制产物缺失时不能宣告完成；
- 至少用一个真实请求验证路由和渐进加载。

### 交付

- 目标 Skill 的官方校验通过；
- 工作区原有修改得到保留；
- 未经用户明确要求，没有提交、推送、发布或外部写入。
