# HAP 已有应用修改工作流

本文件定义 Modify 的唯一执行流程。目标是由 Agent 基于用户要求、线上实时状态和直接依赖自主完成最小修改，不预先生成事务文件，不把历史快照或本地计划当作线上事实。

底层参数按目标读取 `references/spec-*.md` 的相关章节；关联影响和修改方法按需读取 `modify/modify_guide.md`；只有复杂或高风险操作才读取 `modify/safety-rules.md` 与 `modify/execution-boundaries.md`。

## 1. 核心流程

```text
识别用户目标与修改模式
→ 加载目标资产所需的最小规则
→ 读取线上目标和直接依赖
→ 判断必要连带修改与风险
→ 低风险直接执行，中高风险确认范围
→ 合并为最少物理写入
→ 每次写入后立即回读验证
→ 汇报结果、未完成事项和恢复依据
```

线上实时状态是唯一事实源。任何写入都必须能追溯到用户明确要求或为了实现该要求不可缺少的连带修改；可选建议未经用户选择不得执行。

## 2. 修改模式与范围

### 2.1 修改模式

| 模式 | 进入条件 | 行为 |
|---|---|---|
| `direct` | 用户明确说明对象要达到的目标状态，或明确要求新增、删除、迁移、清洗 | 读取实时状态后直接形成最小修改 |
| `audit_repair` | 用户选择 Audit 报告中的具体 `findingId` | Finding 仅用于定位；重新读取目标与直接依赖后修复 |

只说“优化”但没有目标状态时进入 Audit，不在 Modify 中自行扩大问题发现范围。

### 2.2 路由标签

- **目标资产 `assets`**：`app`、`navigation`、`worksheet`、`field`、`relation`、`layout`、`view`、`action`、`rule`、`print_template`、`page`、`chart`、`workflow`、`chatbot`、`role`、`permission`、`record`、`data` 等。
- **复杂场景 `scenarios`**：`physical_delete`、`published_workflow`、`fixed_value_mapping`、`bulk_data_update`、`complex_conversion`、`cross_table_migration`、`dependency_governance`。

### 2.3 首轮安全备份提示（单次提醒）

首次进入 Modify 流程时，Agent 必须在首轮回复中主动告知用户：
> 💡 **操作提示**：修改已有应用涉及线上实时状态变更，存在一定操作风险，建议先在明道云平台对当前应用进行**应用备份/导出**。

**注意**：此提示在整个修改会话生命周期中**仅输出一次**，后续轮次、连带修改、分步执行或确认环节中**严禁重复提示**。

## 3. 最小上下文加载

确定初始目标资产和复杂场景后，运行一次：

```bash
python3 {SKILL_DIR}/scripts/resolve_context.py \
  --mode modify \
  --assets {asset1,asset2} \
  --scenarios {scenario1,scenario2} \
  --render
```

解析器输出本次需要的 Guide 章节和参考文件清单：

1. 已渲染的 Guide 章节直接使用，不再读取 `modify/modify_guide.md` 全文；
2. 对 `references/spec-*.md` 只查找当前操作、字段类型和 MCP 工具需要的章节或示例，不要求阅读全文；
3. 只有命中复杂场景时，才加载安全规则和执行边界全文；
4. 发现新的必要受影响资产或复杂场景时，使用扩大后的完整集合重新解析一次，只补读新增内容；
5. 同一轮中已加载的内容不得在执行前重复加载。

禁止为了留痕生成参考文件哈希、已加载文件清单或规则副本。规则是否适用由当前资产、实际依赖和风险决定。

## 4. 读取线上状态与连带影响

1. **核对目标环境**：确认当前 MCP 环境、组织、应用和目标对象。历史文件、Audit 证据和名称匹配只能帮助定位，不能代替实时核对。
2. **读取目标完整状态**：修改已有字段时必须取得最新完整字段对象；修改视图、角色、工作流等对象时读取能生成安全 payload 的完整配置。
3. **按需读取直接依赖**：只读取完成当前目标所需的一层直接依赖。确有引用、权限、历史数据或运行态风险时再扩展；不得固定扫描整个应用。
4. **自主分类影响**：Agent 在当前会话中区分以下内容：
   - `requested`：用户明确要求；
   - `required_linked`：实现目标不可缺少的连带修改；
   - `recommended`：有价值但非必要，默认不执行；
   - `no_change`：已检查且无需修改；
   - `unresolved`：当前无法确认，不能假设无影响。
5. **权限按风险读取**：新增普通非敏感字段默认继承工作表现有权限，不读取全部角色；新增敏感字段、视图、动作、模板、页面，或用户明确要求权限变化时，才读取相关角色和入口配置。

涉及删除、类型变化、数据迁移、数据源切换、已发布工作流或无法确定的外部引用时，必须加载 `modify/execution-boundaries.md` 并完成其中的依赖影响检查。

## 5. 形成当前执行意图

Agent 在会话中维护当前执行意图，不要求写入 JSON 或本地文件。至少要明确：

- 用户目标和允许修改的对象；
- 必要连带修改及原因；
- 明确不应变化的对象或属性；
- 合并后的物理写入批次及依赖顺序；
- 每个批次的最小回读方式和验证断言；
- 风险等级、人工事项和恢复依据。

写入批次按以下原则形成：

1. 实时状态已经满足目标时直接报告 `no_change`，不得重复写入；
2. 按“写入工具 + 父对象 + 执行阶段”合并兼容变化；
3. 同一工作表的字段增改、同一角色的权限差异、同值记录更新等分别尽量合并；
4. 新 ID 依赖、迁移前后步骤、破坏性清理和相互覆盖的 payload 必须分开；
5. 先创建或修改主体对象，再配置依赖，最后执行迁移后的删除与清理；
6. 执行过程中不得静默加入推荐项或无关修改。范围扩大时重新判断风险；中高风险范围变化后重新向用户确认。

## 6. 风险与确认

| 等级 | 典型条件 | 执行方式 |
|---|---|---|
| 低风险 | 单对象、增量、可逆、依赖明确、不改变历史数据和敏感权限 | 可在简述目标后连续执行 |
| 中风险 | 改变业务行为、多对象联动、一般数据迁移、设置必填或只读、权限变化 | 展示修改范围、连带影响和验证方法，等待明确确认 |
| 高风险 | 物理删除、强制类型变化、大批量生产数据、不可逆迁移、已发布流程重大调整或依赖不明确 | 展示准确对象、数据影响、恢复依据和停止条件，获得专门确认 |

确认绑定用户看到的自然语言修改范围。目标、连带范围、执行方式或风险发生实质变化时，原确认失效；重新展示变化后的范围并确认，不需要计算计划哈希。

## 7. 执行与回读

按依赖顺序逐批执行：

```text
取得目标最新状态（可复用本轮最近一次、仍然完整有效的回读）
→ 核对目标、关键前置条件和受保护属性
→ 由最新状态生成最终 payload
→ 执行一次合并写入
→ 使用最小充分接口回读一次
→ 验证全部预期变化与受保护属性
→ 记录结果并进入下一批
```

- 修改已有字段时，基于刚读取的完整实时对象深复制，只改变目标属性后提交；不得用示例或局部属性列表重建对象。
- 同一物理写入包含多项兼容变化时，只做一次能够覆盖全部断言的回读；一个接口无法覆盖时再补最少专用读取。
- 回读结果可作为后续批次的真实 ID 和最新状态来源；状态未变化且信息充分时不得重复读取。
- 任一断言失败，立即停止依赖该批次的后续操作。
- 写接口超时、断网或结果不明时，第一动作必须回读；只有确认未生效且错误可重试时，最多重试 2 次。
- 只有存在明确反向 API 且不会覆盖其他人的新变化时，才可声明自动补偿；历史快照只能作为恢复参考。

## 8. 跨轮次与高风险运行日志

以下情况创建轻量运行日志：高风险操作、批量数据、多阶段迁移、跨轮次继续、部分成功、存在人工事项。

```text
{WORKSPACE_ROOT}/apps/{appName}/modify-runs/{runId}/
└── execution-log.json
```

日志只记录：用户范围、风险、已完成批次、待执行批次、失败批次、验证结果和人工事项。不得把它扩展成新的预执行事务文件。普通同轮低风险修改默认不落盘；用户要求正式报告时再生成 `result.md`。

恢复执行时不得仅凭日志继续：先重新核对环境和目标实时状态，再根据已经生效的结果决定跳过、补做或停止。

## 9. Audit 修复衔接

用户选择 finding 后：

1. 核对环境、组织、应用、`findingId` 和目标对象；
2. Finding 和审查证据仅作为定位线索；
3. 重新读取目标实时状态和必要直接依赖；
4. 只处理用户选择的 Finding，以及修复它不可缺少的连带修改；
5. 按本工作流完成风险判断、执行和回读；
6. 按需复查原检查项，报告“已解决 / 未解决 / 无法判断”。

## 10. 完成条件

只有同时满足以下条件，才可报告 Modify 完成：

1. 用户目标和必要连带范围已经处理，无未经授权的推荐修改；
2. 每个实际写入批次都已回读并通过全部断言；
3. 状态不明、失败和跳过批次均已如实说明；
4. 未完成的人工事项已经列出责任人、操作路径和完成标准；
5. 高风险或跨轮次任务的轻量执行日志已更新。
