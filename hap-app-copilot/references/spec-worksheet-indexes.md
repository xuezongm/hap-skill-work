## 一、 索引定位与 5 个专属 MCP 工具

工作表索引通过对指定字段建立数据库底层的物理排序结构（B-Tree），在查询、筛选或排序时直接定位符合条件的数据行，避免全表扫描（Full Table Scan），显著提升数万至数十万级大表上的查询响应速度。

### 1.1 专属 MCP 工具清单

| MCP 工具名 | 核心职责 | 关键参数说明 |
| :--- | :--- | :--- |
| **`get_worksheet_index_list`** | 获取工作表全部索引与可用字段 | 入参：`appId`, `worksheet_id`。<br>返回：物理索引列表、可用字段清单（`availableFields`）、已建自定义索引数与配额上限。**创建或更新前必须先调用此接口**。 |
| **`create_worksheet_index`** | 创建普通或唯一物理索引 | 入参：`appId`, `worksheet_id`, `type`, `fields`, `name`（可选）。<br>• `type`: `"normal"`（普通索引）/ `"unique"`（唯一索引）<br>• `fields`: 有序字段数组 `[{ field: "字段ID/别名", mode: "ascending" \| "descending" }]`（1~32 个字段） |
| **`update_worksheet_index`** | 调整已有索引字段、方向或类型 | 入参：`appId`, `worksheet_id`, `index_id`, `type`, `fields`, `name`。<br>当传入 `fields` 时为全量替换数组。 |
| **`rename_worksheet_index`** | 修改索引显示名称 | 入参：`appId`, `worksheet_id`, `index_id`, `name`。 |
| **`delete_worksheet_index`** | 删除冗余或无效索引 | 入参：`appId`, `worksheet_id`, `index_id`。 |

## 二、 平台核心限制与配额约束 (Hard Limits)

1. **自定义索引配额上限**：
   - 每张工作表**最多创建 5 个自定义索引**；
   - 系统内置索引（如自动创建的主键索引 `index_rowid`）**不占用**这 5 个自定义配额；
2. **多选类型字段限制**：
   - 每个复合索引中**最多只能包含 1 个多选类型字段**（包含多选选项、人员、部门、多条关联等）；
3. **系统内置索引保护**：
   - 系统自动创建的 `index_rowid` 索引**不支持修改名称、不支持删除**；
   - 公有云上系统可能根据慢查询日志自动创建分析索引，严禁随意删除非用户创建的系统索引；
4. **写入开销权衡**：
   - 索引并不是越多越好。新增、修改、删除记录时需同步维护索引树；
   - **几万条以下的小表通常无需创建索引**，仅针对 10 万行以上大表、高频筛选或查询出现明显卡顿的场景建立必要索引。

## 三、 复合索引最左前缀匹配与排序规则

### 3.1 最左前缀匹配原则 (Leftmost Prefix Rule)
复合索引的生效严格取决于**索引声明的字段顺序**。

> **示例**：为工作表建立了复合索引 `[ 客户 (A) → 签约日期 (B) → 状态 (C) ]`：
> - ✅ **能够命中索引的查询**：
>   - 仅筛选 `A`（客户）；
>   - 筛选 `A + B`（客户 + 签约日期）；
>   - 筛选 `A + B + C`（客户 + 签约日期 + 状态）；
> - ❌ **无法命中索引的查询**：
>   - 仅筛选 `B`（签约日期）；
>   - 仅筛选 `C`（状态）；
>   - 筛选 `B + C`（签约日期 + 状态，因缺少最左引导字段 A 导致索引完全失效）。

### 3.2 字段区分度与顺序设计
- **高区分度在前**：字段取值重复率越低（唯一值越多），索引过滤效率越高，应优先排在复合索引的最左侧（如：`商品编号` 适合排最前，`性别` 只有两个值不适合排最前）；
- **排序方向与视图一致**：复合索引中每个字段的排序方向（`ascending` 升序 / `descending` 降序），应尽量与高频视图中的默认排序规则保持一致，否则无法利用索引加速排序。

## 四、 唯一索引 (unique) 与空值/回收站避坑

### 4.1 唯一索引核心特性
- **强约束机制**：`type: "unique"` 不仅加速查询，更在数据库层面强制校验索引字段组合的值在全表全局唯一；
- **适用场景**：业务单号（`AutoNumber`）、统一社会信用代码、身份证号、外部系统唯一业务主键、以及业务防重组合（如「人员 + 打卡日期」）。

### 4.2 空值陷阱 (Null Trap)
> [!CAUTION]
> **唯一索引的空值限制**：
> 若唯一索引关联的字段允许为空，**整个工作表中最多只允许存在 1 条该字段为空的记录**！若新增第 2 条空值记录，数据库会判定空值重复并直接报错拦截。
> **最佳实践**：建立唯一索引的字段，在表单中**必须同时设为必填（`required: true`）**。

### 4.3 回收站数据穿透检查
- 创建唯一索引时，系统不仅检查当前活跃记录，还会**穿透检查回收站中的已删除记录**；
- 若提示创建失败但当前列表无重复数据，需进入工作表回收站执行**「立即清空」**，清除历史重复脏数据后重新创建。

## 五、 索引不易命中的 4 类反模式与调优建议

即使已建立了物理索引，若查询或视图过滤条件设计不当，仍然会导致索引失效（回退到全表扫描）：

| 失效场景 / 反模式 | 典型条件示例 | 根本原因 | 调优建议 |
| :--- | :--- | :--- | :--- |
| **① 否定逻辑** | `不等于 (!=)`, `不包含`, `开头不是` | B-Tree 索引无法通过正向目录跳转排查否定集合 | 尽量改写为等值匹配或白名单 `in` 过滤 |
| **② 模糊匹配与空值** | `包含 (like %xxx%)`, `为空 (is_null)` | 无法利用索引的最左前缀顺序定位 | 精确查询优先；避免高频按后缀模糊搜索 |
| **③ 复合“或”逻辑** | `条件 A OR 条件 B` | 只要有一侧缺少索引，整体将退化为全表扫描 | 尽量使用 `AND` 组合；高频组合建立复合索引 |
| **④ 拼音排序与低区分度** | 文本字段开启“按拼音排序”；状态值单一选项占比 > 30% | 拼音重排绕过了二进制索引顺序；选择性过低导致优化器放弃索引 | 避免在大表文本字段上开启拼音排序；高频状态建议与高区分度字段联合建复合索引 |
