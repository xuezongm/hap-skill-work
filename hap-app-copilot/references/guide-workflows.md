## 一、 设计分析流程（7 维度逐项分析）

> [!CAUTION]
> **intentHints 只描述了用户显式提到的动作，通常只覆盖核心路径的 30-50%。你必须结合 worksheetContext 中的表结构、字段和关联关系，以及 roles 中的角色信息，主动补全 intentHints 未提及的关联表联动、状态回写、通知提醒和异常分支。只翻译 intentHints 而不补全是不合格的设计。**

拿到每条工作流后，**必须逐项分析**以下 7 个维度：
1. **触发时机**：触发时这条记录处于什么业务状态？有哪些字段已有值？
2. **主表更新**：触发后，主表的哪些字段需要更新？（状态、时间戳、操作人等）
3. **关联表联动**：逐表扫描 worksheetContext——这次变化会影响哪些关联表？需要查询和更新什么？**这是最容易遗漏的维度，必须逐表检查。**
4. **是否需要审批**：这个业务动作是否涉及人工审核？审批通过/否决后分别如何处理？
5. **分支细化**：是否存在多种业务情况需要区分处理？
6. **通知策略**：谁需要知道这件事？用什么方式通知？**大多数业务变更都需要通知相关方。**
7. **异常处理**：查不到数据怎么办？状态不符合预期怎么办？

## 二、 16 种可用节点类型速查

| type | 名称 | 用途 |
|---|---|---|
| `get_single` | 查询单条记录 | 按条件从指定工作表查询一条记录 |
| `get_multiple` | 查询多条记录 | 按条件查询多条记录 |
| `update_record` | 更新记录 | 更新指定记录的字段值 |
| `add_record` | 新增记录 | 在指定工作表中新增一条记录 |
| `delete_record` | 删除记录 | 删除指定记录 |
| `branch` | 条件分支 | 根据字段值条件进入不同处理分支 |
| `sub_process` | 子流程 | 对多条记录逐条执行一组节点 |
| `approval_block` | 审批流程 | 审批容器，内部包含 approve、fill_in 节点 |
| `approve` | 审批节点 | 发起人工审批（只能在 approval_block 内使用） |
| `fill_in` | 填写节点 | 发起人工填写（只能在 approval_block 内使用） |
| `rollup` | 汇总统计 | 对工作表或查询出的记录做聚合运算（count/sum/avg/max/min） |
| `compute` | 运算 | 数值公式、日期差值或日期偏移 |
| `delay` | 延时 | 等待指定时长后继续执行 |
| `cc` | 抄送 | 将记录详情通知给指定人员查看（仅单条记录） |
| `send_internal_notice` | 站内通知 | 发送站内消息通知（不需要数据源） |
| `send_email` | 发送邮件 | 发送邮件通知 |
| `code` | 代码块 | 编写自定义代码处理复杂逻辑 |

## 三、 核心设计原则

### 1. 关联表联动（必须检查）
每条工作流触发时，**逐表扫描** worksheetContext：
- 子表记录变化 → 主表的统计字段（数量/金额）或状态字段是否需要更新？
- 主表字段修改 → 关联的子表记录是否需要同步？
- 记录状态变更 → 其他业务表的可用数量、占用状态是否受影响？

### 2. 前置数据查询（先查后用）
更新**其他工作表**的记录前，必须先安排查询节点：
- 触发记录本身可直接操作；
- 其他表的记录必须先通过查询获取，然后再更新；
- 定时触发的工作流没有触发记录，必须通过查询获取待处理数据。
> ⚠️ **`update_record` 节点没有输出 controls**：后续通知/更新节点**不能**引用 `update_record` 的结果字段，应追溯引用**触发记录**或**查询节点**的字段。

### 3. 状态流转完整性
- 主记录状态更新 → 同步写入时间戳（完成时间、审批时间）；
- 同步记录操作人（审批人、处理人）。

## 四、 分支处理与判空铁律

> [!CAUTION]
> **分支节点的 paths 数组至少包含 2 条路径**——平台 API 会拒绝单路径分支（`paths must have at least 2 items`）。即使业务只有一种条件需要处理，也必须补一条"其他"（默认/兜底）路径。

### 查询结果分支判空规范
- **`get_single` 结果分支**：直接在分支条件中判断该查询节点的 `rowid` 是否为 `not_empty`；
- **`get_multiple` 结果分支**：**绝对严禁**直接判断 `get_multiple` 的 `rowid`。必须采用二阶段逻辑：
  1. 先紧随其后创建一个 **`rollup`（汇总统计）** 节点（对查询结果做 `COUNT` 聚合）；
  2. 在 downstream 的 `branch` 分支中判断该 rollup 节点输出的 **`number_fx_id > 0`**。

## 五、 子流程与审批块封闭作用域规则

> [!CAUTION]
> 子流程（`sub_process`）与审批块（`approval_block`）是**完全独立的封闭作用域**。

1. **子流程 (`sub_process`)**：
   - 遍历的当前记录固定使用 `{ nodeAlias: "sub_trigger" }` 引用；
   - 引用外层主流程数据时，必须通过 `inputFields` 声明参数并在 `config.input` 赋值，在内部通过虚拟别名 `process_variable` 引用；
2. **审批块 (`approval_block`)**：
   - 被审批记录固定使用 `{ nodeAlias: "approval_start" }` 引用；
   - 必须显式指定 `initiators`（发起人）；
   - 审批内部结果（审批人 `executorid`、审批意见 `opinionSummary`）在 `approve` 节点后加 `branchType: "approval_result"` 写入记录；
   - 主流程结果（`PASS` / `OVERRULE`）在 `approval_block` 外部主流程用 `branch` 处理。

## 六、 通知与提醒策略补全

- **站内通知**：优先选 `cc`（带单条记录链接，收件人可看详情）；无关联记录时选 `send_internal_notice`；
- **邮件通知**：`send_email` 用于向记录中的邮箱字段发送邮件；
- ⚠️ **外部门户角色限制**：以角色为接收人时，外部门户角色（`roleScope: "externalPortal"`）不支持 `cc` 和 `send_internal_notice`，应改用记录上的**人员字段**引用或 `send_email`；
- **通知正文高标准**：`content` 必须写出完整的业务文案，通过占位符嵌入单号、日期、金额等上下文。

## 七、 设计自检 11 项清单

1. ✅ 7 个维度是否全部逐项分析？（尤其关联表联动和通知策略）
2. ✅ 每个 `update_record` 的数据来源是否明确？更新其他表前面是否有查询节点？
3. ✅ 选项字段的值是否来自 worksheetContext 中的实际选项？
4. ✅ 触发的关联表是否全部扫描过，该联动的都安排了节点？
5. ✅ 通知接收人是否明确（`字段：XX（来源节点）` / `角色：XX`）？
6. ✅ 有分支的地方 paths 是否 ≥ 2 并覆盖了所有路径？
7. ✅ 边界场景是否处理（查不到数据、条件不满足等）？
8. ✅ `get_multiple` 后需要逐条处理的场景，是否使用了 `sub_process`？
9. ✅ 子流程内部引用外层数据时是否通过 `inputFields` 参数桥接？审批块内部是否仅引用 `approval_start` 或内部查询？
10. ✅ 后续节点引用字段时，是否来自触发记录或查询节点（而非 `update_record`）？
11. ✅ 审批块是否指定了发起人？内部是否包含至少 1 个审批节点？
